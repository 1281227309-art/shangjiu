## 1. 第一部分：视觉审查

审查对象：当前线上平台 `geo.shangjiudistillery.cn` 的实际样式产物
（`index-Cph21x1F.css`，28.6 KB）。以下结论均基于对该文件的解析与 WCAG 2.1 公式的实测计算，
不是主观印象。

### 1.1 颜色

**现状**：样式产物中实际出现 **28 个不同颜色**，分布在 **7 套 Tailwind 默认色阶**里
（teal / slate / gray / blue / green / red / amber），并存在明显的冗余近重复：

| 冗余现象 | 具体色值 | 问题 |
| --- | --- | --- |
| 两套「危险红」 | `#DC2626`(red-600) + `#B91C1C`(red-700) | 同一语义两个值，不同页面会给不同深浅 |
| 两套「浅绿底」 | `#ECFDF5`(emerald-50) + `#F0FDF4`(green-50) | 肉眼几乎无差别，无意义地扩大色板 |
| 两套「边框灰」 | `#E2E8F0`(slate-200) + `#E5E7EB`(gray-200) | 分隔线深浅不一致 |
| 两套「青绿」 | `#0F766E`(teal-700) + `#115E59`(teal-800) | 主色与其深色态混用 |
| **蓝色已零散出现** | `#3B82F6`(blue-500) | 站点事实上已在「青绿主色 + 零星蓝色」之间摇摆——这本身就是品牌色需要收敛的信号 |

主色是 `#0F766E`（青绿），强调色是 `#B45309`（琥珀）。
**28 个颜色、7 个色族、却没有任何一层语义映射**，正是下面几个对比度问题反复出现的根因。

| 问题 | 实测证据 | 影响 |
| --- | --- | --- |
| **辅助文字对比度不达标（P0）** | `#9CA3AF`（gray-400）在白底 **2.54:1**、在页面底 `#F8FAFC` **2.43:1** | 低于 WCAG AA 正文要求的 4.5:1。占位符、时间戳、次要说明这类文字，弱视用户基本读不到 |
| **错误态文字在浅红底上不达标** | `#DC2626` 在 `#FEF2F2` 上 **4.41:1** | 差 0.09 未达 4.5:1。错误提示恰是最需要看清的文字 |
| **焦点环几乎不可见（P0，最严重）** | 全局 `:focus` 的 ring 为 `rgb(15 118 110 / .2)`；20% 青绿混白后为 `#CFE4E2`，对比度 **1.33:1** | WCAG 1.4.11 要求非文本对比度 ≥3:1。**键盘用户的焦点指示基本等于没有**，这是纯键盘可操作性的硬伤 |
| **无深浅色阶体系** | 28 个颜色混用 7 个色族，没有成体系的 50–900 色阶 | hover / 选中 / 浅底 / 边框等状态只能临时拼凑，是上面几条问题反复出现的根因 |

**改进方向**：建立**完整色阶 + 语义令牌**两层结构（§2），并把「对比度」变成可执行断言而不是评审意见。
本次交付的 [check-contrast.mjs](tools/check-contrast.mjs) 就是这套断言，可以直接接进 CI。

### 1.2 排版

| 问题 | 实测证据 | 建议 |
| --- | --- | --- |
| **中文字号过小** | 样式中存在 `10px`、`11px` 两级字号 | 中文方块字在这两级下辨识度很差。正文最小 12px，辅助信息不少于 12px，说明性文字用 13px |
| **两套字号体系混用** | 既有 Tailwind 的 `rem` 阶梯（`.75rem`–`2.25rem`），又有手写的 `px`（10/11/12/13/15） | 统一到一套 px 阶梯（见 §2.4），中文界面用 px 比 rem 更可控（避免根字号被浏览器设置放大后撑破布局） |
| **行高未针对中文调优** | — | 中文需要比拉丁文更松的行距。正文行高取 1.5–1.6（本设计：15px/24px = 1.6） |
| **字体栈是泛型系统栈** | `-apple-system, BlinkMacSystemFont, …, sans-serif` | ⚠️ **这一点会直接影响第二部分的实现**：若接入 Pretext，`system-ui` / `-apple-system` 在 macOS 上**测量不准**（上游明确列为已知问题）。必须改用**具名字体**，且 CSS 与 canvas 的字体必须一致（§3.3） |

### 1.3 间距与圆角

| 问题 | 实测证据 | 建议 |
| --- | --- | --- |
| **无间距标尺** | padding/margin/gap 取值散乱，无统一倍数关系 | 统一到 4px 基准、8pt 为主序列：`4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48` |
| **圆角不自洽** | 同时存在 `2 / 6 / 8 / 12px / .75rem(=12px) / 9999px` —— 12px 有两个来源 | 收敛为 6 档：`6 / 8 / 12 / 16 / 20 / 999px`，并按「容器 > 子元素」的规则取用（本设计：气泡 16px、卡片 12px、输入 16px、胶囊 999px） |
| **断点偏少** | 仅 `640 / 768 / 1024 / 1280`（Tailwind 默认） | 增补 320–430px 的窄屏规则。本次实测在 320px 下暴露了 3 处真实缺陷（§3.7） |

### 1.4 可访问性（除对比度外）

| 问题 | 实测证据 | 影响 |
| --- | --- | --- |
| **完全不支持「减少动效」** | 全文 `prefers-reduced-motion` 出现 **0 次**，但同时大量使用 `transition-all` | 前庭功能敏感的用户无法关闭动效。GEO 平台这类「扫描 / 采集进度」动画尤其需要该开关 |
| **焦点仅靠 box-shadow** | `:focus { outline: 2px solid transparent; … box-shadow: ring }` | 一旦 box-shadow 失效（强制高对比模式 `forced-colors` 下浏览器会丢弃 box-shadow），**焦点完全不可见** |
| **无 `forced-colors` 适配** | 无相关媒体查询 | Windows 高对比模式下可能出现「有边框但看不见」的控件 |
| **无打印样式** | 无 `@media print` | 平台的核心产出是**诊断报告**。报告打印/另存为 PDF 是真实高频场景，却按屏幕样式输出 |

**改进方向**：本次交付已逐条实现对应方案，见 §3.5。

### 1.5 审查结论与优先级

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| **P0** | 焦点指示可见性（≥3:1，且不依赖 box-shadow 单独承载） | 直接影响键盘用户能否使用；且属法规常见的合规检查项 |
| **P0** | 辅助文字 / 占位符 / 错误态文字对比度 | 大量高频文字不达标 |
| **P0** | 建立完整色阶与语义令牌 | 上面两类问题的根因 |
| **P1** | 中文字号下限、行高、间距标尺、圆角收敛 | 观感与一致性问题，改动面大但不紧急 |
| **P1** | `prefers-reduced-motion`、`forced-colors` | 成本低、收益明确 |
| **P2** | 打印样式（诊断报告） | 业务价值明确，可独立迭代 |
| **P2** | 品牌色从青绿切换为蓝 + 白 + 橙 | 定位表达问题：青绿偏「金融 / 医疗」，与「生成式引擎 / AI」的品类联想不匹配 |

## 2. 第二部分：品牌色体系（蓝 + 白 + 橙）

### 2.1 三层结构

```
第一层  色阶（ramp）      完整、等距、不直接使用
第二层  语义令牌（token）  按用途命名，界面只引用这一层
第三层  组件              只消费语义令牌，不写死色值
```

这样做的收益：换品牌色只改第一层；深浅主题只改第二层映射；组件代码零改动。

### 2.4 橙色使用硬约束（**本节是本次设计最重要的一条规则**）

「橙色点缀」听起来是审美问题，实际是**可用性问题**。橙色明度高、与白底的对比度天然偏低：

| 组合 | 实测对比度 | 门槛 | 结论 |
| --- | --- | --- | --- |
| `#F76B0C`（橙 500）**当正文** | **2.97:1** | 4.5:1 | ❌ 禁止 |
| `#FFFFFF` 白字**压橙 500 底** | **2.97:1** | 4.5:1 | ❌ 禁止 |
| `#DC5204`（橙 600）作**功能性图形** | **4.00:1** | 3:1 | ✅ 允许（图标、指示条、状态点） |
| `#B53E08`（橙 700）作**文字** | **5.74:1** | 4.5:1 | ✅ 允许 |
| `#8F330E`（橙 800）文字压橙浅底 | **5.41:1** | 4.5:1 | ✅ 允许 |
| `#0B1220` 深字压橙 500 底 | **6.30:1** | 4.5:1 | ✅ **橙色按钮的正确做法：深色字，而不是白字** |
| `#FFAE6E`（橙 300）深色主题文字 | **10.28:1** | 4.5:1 | ✅ 深色主题下橙色才可安全承载文字 |

**落地规则**：

1. 橙色**永不**作为正文颜色，**永不**配白字。
2. 浅色主题下，橙色只做三件事：**功能性图形**（用 600）、**文字强调**（用 700）、**浅底块**（50–200）。
3. 需要橙色实心按钮时，文字用深色（`#0B1220`），对比度 6.30:1。
4. 深色主题下橙色可以放宽（`#FFAE6E` 达 10.28:1），这也是「点缀」在深色主题里更醒目的原因。

这 4 条已写成可执行断言：`check-contrast.mjs` 里的 `constraint` 类断言会断言
「橙 500 当正文**确实不达标**」——如果哪天有人改了色值让它「变达标了」，
门禁会报 `REVIEW` 提醒重新评审设计文档，而不是静默放过。

## 3. 第三部分：交付 HTML 的设计与实现

### 3.1 为什么引入 Pretext

[Pretext](https://github.com/chenglou/pretext)（`@chenglou/pretext` v0.0.9）是一个
纯 JavaScript 的**多行文本测量与排版库**：它在不读取 DOM 几何的前提下算出文本要占多高、多宽。
它解决的是 AI 对话界面的三个具体问题——也正是我们这次要展示的：

| 场景 | 常规做法 | 引入 Pretext 后 |
| --- | --- | --- |
| **气泡紧贴内容** | `max-width: 70%`，短句「好的」也占满 70%，很粗糙 | 直接拿到「最宽那一行」的宽度，气泡贴合内容（本次实测：短消息气泡 361px / 可用 762px） |
| **流式输出** | 每个 token 都要测一次高度 → 每次都读 DOM → 滚动抖动 | 纯算术判断「行数有没有变」，**只有行数变了才动滚动** |
| **输入框自适应高度** | 每次按键读 `scrollHeight` → 强制重排 | 用 `pre-wrap` 模型纯计算，**不读 DOM** |
| **避免布局跳动** | 回答到达时高度突变，把滚动位置顶走 | 提前算出最终高度并预留（引用胶囊行同理，用 `rich-inline` 预估换行行数） |

**实际用到的 4 个上游 API**：`prepare` / `layout`（高度）、
`prepareWithSegments` + `measureLineStats`（紧贴宽度）、
`prepare(..., {whiteSpace:'pre-wrap'})`（输入框）、
`prepareRichInline` + `measureRichInlineStats`（引用胶囊换行预估）。

### 3.2 交付形态：为什么是「单文件、零依赖」

一个容易踩的坑：**ES module 在 `file://` 下会被 CORS 拦截**（origin 为 `null`），
如果直接用 `<script type="module">` 引入 Pretext，客户**双击打开就是白屏**。

因此构建流程做了三件事（见 [build.mjs](tools/build.mjs)）：

1. 把 Pretext 打成 **IIFE 经典脚本**（[vendor/pretext/pretext.iife.js](vendor/pretext/pretext.iife.js)，51 KB）
2. 内联进 HTML —— 经典脚本在 `file://` 下可正常执行，且 `Intl.Segmenter` / Canvas 均可用
3. 不引用任何 CDN

> **为什么不用 CDN**：`esm.sh` / `jsdelivr` 在国内并不总是可达。对一个要交付给客户的
> 单页设计稿而言，「打开就能看」比「体积最小」重要得多。若后续希望走 CDN，
> 只需替换 §附录 B 的构建命令。

构建脚本自带三道自检（占位符未替换 / `</script>` 数量异常 / 内联尾部缺失即报错）。
这三道自检不是形式主义——**构建期真的抓到一个 bug**：压缩后的 JS 含 `$&`、`` $` ``、`$'` 序列，
若把 bundle 作为**字符串**传给 `String.replace()`，JS 会把它们当替换模式展开，
把 `</script>` 注入脚本中间导致内联脚本被静默截断、页面退化为 DOM 回退且只报一句
`Invalid or unexpected token`。修法是改用**函数形式**的替换值。详见构建脚本注释。

### 3.3 字体：Pretext 集成里最容易出错的一环

Pretext 的上游注意事项明确写着：**`system-ui` / `-apple-system` 在 macOS 上测量不准，
必须用具名字体**；并且 canvas 的 `font` 字符串必须与 CSS 的
**字号、字重、字族三者完全一致**，否则算出来的高度是错的——而且错得很隐蔽。

本次的实现方式：

1. **运行时探测**：用 canvas 宽度比对法，从 `PingFang SC / HarmonyOS Sans SC /
   Microsoft YaHei / Source Han Sans SC / Noto Sans CJK SC / Hiragino Sans GB`
   中挑出本机真实可用的那一支（实测本机解析为 `PingFang SC`），等宽字体同理（`SFMono-Regular`）。
2. **探测结果写回 CSS 变量**，使 CSS 渲染与 canvas 测量用的是同一支字体。
3. **排版尺度以 CSS 为唯一事实来源**：JS 从 `:root` 读取 `--t-body-size` 等令牌再拼 canvas 字体串，
   避免「CSS 改了、JS 没改」的漂移。
4. **字重也要对齐**：`lead` 是 17px/600、用户气泡正文是 15px/**500**、
   普通正文是 15px/400，各自有独立令牌并分别测量。少对齐一个字重，气泡就会刚好卡在换行点多出一行。

**测量精度实测**：5 段文本（纯中文 / 中英混排 / 极短 / 长句）× 5 种宽度 = 25 个组合，
Pretext 高度与浏览器真实排版**最大偏差 0px**（25/25 完全一致）。
这条如果不过，整套 Pretext 方案就不成立，所以它是验证脚本里的第一优先项。

**v1.1 补上的一环：段内混排字重。** v1.0 按「块」对齐了字重（小标题 600、用户气泡 500、
正文 400），但一段话**内部**的局部加粗仍按 400 估算——这是 v1.0 自己列出的限制。
v1.1 改用 Pretext 的 `rich-inline` 入口逐片段测量：把段落拆成「常规片段 / 加粗片段」，
每段用各自真实的 canvas 字体串。实测 16 组样本（含 `**A**b**C**d**E**f` 这类字重交替的极端串）：

| 方案 | 最大高度偏差 |
| --- | --- |
| 忽略字重的纯文本估算（v1.0） | **72px**（整整 3 行） |
| `rich-inline` 逐片段测量（v1.1） | **0px** |

实现上还绕开了一个坑：`rich-inline` 的接口有意保持窄（仅 inline、仅 `white-space: normal`），
因此遇到不支持的输入会退回纯文本测量并计数（`stats.richFallback`），不会整块失败。
另外 DOM 是唯一事实来源——测量时用 `mdFromNode()` 把段落**还原**成 `**加粗**` 形式，
静态种子内容与 JS 生成内容因此走同一条路径，不必额外维护 `data-md` 属性。

### 3.4 响应式断点

| 断点 | 布局 | 会话栏 | 诊断面板 |
| --- | --- | --- | --- |
| ≥1200px | 三栏 `264 / 1fr / 336` | 常驻 | 常驻右栏 |
| 900–1199px | 两栏 `1fr / 320` | 收为抽屉 | 常驻右栏 |
| 560–899px | 单栏（诊断条在上） | 抽屉 | **可折叠**：收起时一行摘要（`65 可见度 · 豆包 68% · 千问 0%`）；展开为横向卡片条，高度有界（`min(34vh,240px)`），超出由卡片内部滚动承接 |
| ≤560px | 单栏紧凑 | 抽屉 | 卡片收窄至 210px；隐藏跳转分隔线 |
| ≤430px | 极窄 | 抽屉 | 隐藏装饰性头像，保证品牌名与控件不被裁切 |

布局用 `grid-template-areas` 表达，三个区域在断点间**只换位置、不重复 DOM**——
抽屉不是「另做一份移动端菜单」，而是同一份会话列表换成了浮层定位
（好处：`aria-current`、事件绑定、焦点逻辑都只有一份）。

**v1.1 修掉的取舍**：v1.0 在移动端把诊断面板做成「有界卡片条」，理由是保证输入区可见，
但代价是 320px 矮屏上对话区只剩约 190px。v1.1 改为**默认收起**：
收起时只剩 44px 高的一行摘要，输入区与对话区都拿回空间；展开时仍受高度上界保护。
实测 **320×700 在收起与展开两种状态下，输入区都在视口内**。
另外桌面端强制展开——否则会出现「在手机上收起 → 拉宽到桌面 → 面板不见了且无法展开」。

**v1.1 新增的交互（对齐真实对话产品的行为）**：

- **停止生成**：流式期间发送键变为「停止生成」（Esc 也可）。
  中断后**只保留已经生成出来的文字**，不把没等到、也没要求的内容补上——
  否则「停止」之后反而多出内容，复制出来的也对不上。实测：停止时保留 31 字，
  续写完成后 190 字，两者可对比验证。
- **继续生成**：从断点接着写，而不是从头重来；时间轴也接着原进度走，
  避免续写后突然按初始速率爆发。
- **离线失败态 + 重试**：判定依据是**真实的 `navigator.onLine`**，不是伪造的开关——
  把浏览器切离线再发消息就会走到这里，因此能在客户现场「拔网线」复现，
  也**可被自动化测试覆盖**（Playwright 的 `context.setOffline(true)`）。
  失败态是浅红气泡 + 明确原因 + 「重试」，不是一句干巴巴的失败文案。
- **断网提示**：离线时输入区显示 warning 色提示（`role="status"`），恢复网络自动消失。
- **真实打字节奏**：由帧驱动改为**时间驱动**（约 55 字/秒）。
  原来的帧驱动会跑到约 120 字/秒，长回答一闪而过，反而看不出「流式」。

  修法是按「实际是否溢出」动态赋 `tabindex="0"` + `role="group"` + `aria-label`：

  这条规则手写检查想不到，是引入成熟规则引擎的直接收益。

`data-metrics` 变为 `dom`，页脚徽章如实显示「DOM 回退测量 N 次」，
界面与功能不变，仅性能与精度下降。这条路径同样跑通了全部交互断言。

### 3.8 性能实测（v1.1 新增）

工具：[tools/bench-long-chat.mjs](tools/bench-long-chat.mjs)（真实 Chromium，页面内计时）。
**先量再改** —— 下面的数字直接决定了要不要为长会话引入虚拟列表。

**① 高度图计算：Pretext vs DOM 测量**（同一批消息，宽度 640px）

| 条数 | Pretext | DOM 测量 | 倍率 | 每条 | 算出的总高度 |
| --- | --- | --- | --- | --- | --- |
| 50 | 7.3ms | 3.6ms | 0.5× | 146µs | 完全一致 |
| 200 | 2.9ms | 12.0ms | 4.1× | 14.5µs | 完全一致 |
| 500 | 3.5ms | 31.4ms | 9× | 7µs | 完全一致 |
| **1000** | **4.3ms** | **62.8ms** | **14.6×** | **3.8µs** | **完全一致** |

1000 条消息的高度图用 Pretext 只要 **4.3ms**，且**总高度与浏览器真实排版完全一致**。
这印证了 v1.0 路线图里那条判断，也说明虚拟列表的地基（准确、廉价的高度图）已经具备。

**② 修掉一个 41× 的性能缺陷（v1.0 遗留）**

基准第一次跑出来就抓到问题：灌入 2000 条消息后，**测量花了 31,193ms**（渲染只用 201ms）。
根因是最经典的**布局抖动（layout thrashing）**：`applyTightWrap` 逐条执行
「读几何（`clientWidth` / `offsetWidth` / `getComputedStyle`）→ 写 `style` → 再读下一条」，
每次写入都把布局标记为脏，下一次读取又必须重新布局整棵 3.2 万节点的文档，
于是 1000 次迭代退化成 1000 次全文档重排。

修法是把**读取阶段与写入阶段彻底分开**：一批测量开始前一次性读完行宽/头像宽/间距
（这些值对所有消息本来就是同一个），之后只做纯计算与写入。

| 指标 | 修复前 | 修复后 | 提升 |
| --- | --- | --- | --- |
| 2000 条消息的紧贴测量 | **31,193ms** | **764ms** | **41×** |

> 这个缺陷尤其值得记一笔：引入 Pretext 的**初衷**就是避免测量引发重排，
> 而我在宽度计算里又把重排引了回来 —— 而且它在 3–5 条消息的演示里完全看不出来。
> 只有把规模放大到 2000 条，它才暴露。**性能问题必须用规模去测，不能靠看。**

**③ 长会话降载：`content-visibility`**

数据说明真正的瓶颈不在测量（1000 条只要 4.3ms），而在 **DOM 节点数（3.2 万个）与重排代价**。
因此没有引入 JS 虚拟列表，而是交给浏览器的 `content-visibility: auto` ——
屏幕外消息不布局不绘制，且**不需要我们维护高度估算与滚动锚点**，
从根上避开了虚拟列表最容易出的滚动漂移。仅在消息数 > 60 时启用。

| 指标 | 关闭（对照） | 开启 | 变化 |
| --- | --- | --- | --- |
| 强制同步布局（弄脏全部列表后重排） | 35.6ms | **18.1ms** | **−49%** |
| 滚动 40 次的超 16.7ms 帧数 | 0/40 | 0/40 | 本来就达标 |

**如实说明**：滚动帧时间在 2000 条消息下**本来就达标**，`content-visibility` 的收益体现在
「布局被作废时」——窗口缩放、字体加载完成、主题切换、追加消息。
所以它是一条**降低最坏情况**的措施，而不是「让滚动更顺」的宣传点。

**④ 真实渲染**：2000 条消息 = 渲染 202ms + 紧贴测量 758ms ≈ **0.96s**（一次性），
DOM 节点 32,875 个。若要支持更长的会话，下一步可做的是**只重测可见消息**
（同样的虚拟化思路用到「测量」而非「渲染」上），而不是急着上完整虚拟列表。

2. **替换不达标的文字色**：`gray-400` 文字（2.54:1）、`red-600` 压浅红（4.41:1）、
   占位符与输入框边框（边框 2.56:1，低于 1.4.11 的 3:1）。可直接搬用本次的
   `--text-muted #5A6A80`（5.51:1）、`--danger #C02626`（5.41:1）、`--border-strong #7E8FA6`（3.30:1）。
3. **把对比度门禁接进 CI**：`node tools/check-contrast.mjs --from-html <产物>` 退出码非 0 即失败。
   这一步的价值在于**它是一次性的**——此后任何一次改色都不会再悄悄破坏可访问性。

### P1 — 一到两个迭代

4. **令牌化落地**：把 §2 的色阶/语义令牌写进 Tailwind 配置（`theme.colors`）或 CSS 变量层，
   收敛掉现在散落的 28 个色值与 7 个色族；同步统一字号（12–30px 六档，去掉 10/11px 两档）、
   间距（4px 基准八档）、圆角（6/8/12/16/20/999）。
5. **补齐偏好适配**：`prefers-reduced-motion`（当前 0 处）、`prefers-contrast`、`forced-colors`。
6. **接入真实流式数据**：本次交付的流式是**模拟的**（前端逐字揭示预设回答）。
   接真实 SSE/WebSocket 时，Pretext 的用法不用改——把 `plain.slice(0, i)` 换成
   真实累积文本即可，`layout()` 判行数变化的逻辑完全复用。
   已实现的停止/继续/失败重试状态可以直接承接真实的 abort 与错误码。
7. **只重测可见消息**（v1.1 更新，取代原「上虚拟列表」）：基准显示**测量已不是瓶颈**
   （1000 条高度图 4.3ms），`content-visibility` 也已把屏幕外消息的布局成本砍掉约一半。
   真正会随会话增长的是「窗口缩放时对所有消息重跑紧贴」这一次性成本（2000 条约 758ms）。
   下一步只需在长会话模式下**只重测视口内消息**，其余滚动进来时再测——
   这是把同一个虚拟化思路用在「测量」而非「渲染」上，代价远小于完整虚拟列表。

### P2 — 进阶

8. **颜色主题可配置**：把第一层色阶做成可注入的 JSON，支持客户自定义品牌色时**自动重算对比度**
   并拒收不达标组合（直接复用 [check-contrast.mjs](tools/check-contrast.mjs) 的数学与约束断言）。
9. **i18n / RTL**：Pretext 支持多语言换行（含 bidi 分段信息），
   若平台要做海外市场 GEO，现在就把文案抽离、并预留 `dir="rtl"` 的镜像规则成本最低。
10. **字体自托管**：若确定不能依赖用户系统字体（例如要保证所有终端视觉一致），
    需自托管一份中文可变字体并 `@font-face`，同时把它作为 Pretext 的测量字体。
    注意中文字体体积大，需子集化（建议按常用字 3500 字 + 动态补充）。
11. **完整虚拟列表**：只有在会话长到数千条、且「只重测可见消息」也不够时才需要。
    届时地基已经具备——高度图 3.9µs/条且与真实排版完全一致（§3.8）。

> **v1.1 已完成的路线图项**：原 P1-7「长会话虚拟滚动」→ 已用基准重新评估并降级（见上）；
> 原 P2-8「诊断报告打印样式」→ **已完成**（§3.5 打印行 + `preview/print-report.png`）；
> 原 P2-9「引入 axe-core」→ **已完成**（[verify-a11y.mjs](tools/verify-a11y.mjs)），并且当场抓到一个真实缺陷。

## 5. 已知限制与取舍（如实说明）

1. **回答内容是预设的**：这是设计交付稿，AI 回答为前端内置示例，未接后端/AI 服务。
2. **引用来源指向平台自身的信源详情路由**（`geo.shangjiudistillery.cn/sources/…`）：
   原型内使用，接入后端时替换为真实来源 URL 即可；已带 `target="_blank" rel="noopener noreferrer"`。
3. **Pretext 是 0.0.x 版本**：API 仍在演进。建议**锁定 `0.0.9`**（本次已把源码与打包产物一并交付并锁定）。
   其上游限制包括：需要 `Intl.Segmenter` + Canvas 2D；极窄宽度下的软连字符、
   emoji 紧邻标点、零宽空格换行可能与浏览器略有差异；**泛型字体（`system-ui`）测量不准**。
4. **结构化气泡不做紧贴（有意为之）**：含列表 / 指标 / 快照 / 引用胶囊的气泡保持满宽。
   原因：这些子块各有自己的最小宽度，强行收窄只会让内部换行变难看；而且这类消息本来就会铺满宽度。
   这些气泡的高度仍由 Pretext 精确参与（流式预留、引用胶囊换行预估）。
5. **`rich-inline` 的窄接口**：它有意只支持 inline + `white-space: normal`。
   本设计的段落都符合，遇到不支持的输入会自动退回纯文本测量并计数（`stats.richFallback`），
   不会整块失败——但若将来引入嵌套标记或多级字重，需要自建更细的测量层。
6. **离线失败态是「真离线」触发的**：要看到失败态，需要真的断网（或 `context.setOffline(true)`）。
   这是刻意的：比一个隐藏的「模拟失败」开关更可信，也让自动化测试能覆盖它。
7. **`content-visibility` 的浏览器支持**：Chrome / Edge / Safari 18+ / Firefox 125+ 支持；
   不支持时该规则被忽略，界面与功能不受影响（只是失去这项优化）。
   主运行环境（Chromium 内核）已完整支持。
8. **`role="log"` 与虚拟化的取舍**：本次没有引入 JS 虚拟列表，也正因为如此，
   `role="log"` 的语义、find-in-page 与屏幕阅读器线性浏览都保持完整——
   这是选择 `content-visibility` 而非虚拟列表的一个额外理由。
9. **验证覆盖范围**：axe-core 覆盖 5 个界面状态（桌面浅/深、移动收起/展开、失败态），
   自动化规则零违规；但**仍未在真实屏幕阅读器上人工走查**，
   建议上线前用 NVDA / VoiceOver 各过一遍主流程（尤其是流式播报策略与折叠面板）。

## 附录 C：把对比度门禁接进 CI

门禁有两种模式，建议**两种都跑**：

- `node tools/check-contrast.mjs` —— 校验设计令牌表本身（改色阶时立刻发现）
- `node tools/check-contrast.mjs --from-html <构建产物>` —— 校验**实际发出去的那份 CSS**
  （防止「令牌表改了、产物没跟上」的漂移）

两者退出码均为：全部通过 `0`；存在 `require` 不达标或 `constraint` 被推翻则 `1`。
后者是刻意设计的：`constraint` 断言的是「橙 500 不能当正文」这类**已知约束**，
一旦它变成达标，说明色值被人改过，需要重新评审设计文档，而不是静默通过。

```yaml
# 示例：GitHub Actions
- name: 对比度门禁
  run: |
    node tools/build.mjs
    node tools/check-contrast.mjs
    node tools/check-contrast.mjs --from-html geo-ai-assistant.html
```
